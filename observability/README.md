# Maintenance observability configuration

Source configuration for #9; **not deployed**. Uses the approved 99.5% technical-success target (seven-day rolling evaluation), failed outbox > 0, pending growth for at least fifteen minutes, and removal-retry failures > 0. p95 duration is charted in seconds without an invented latency target. Expected caller rejections are not technical failures. Empty traffic is unknown; never replace a missing denominator with 100%.

`project/slo` and `project/alerts` are Monaco configurations. `dashboard.json` is a new, importable Dynatrace dashboard document (not an overwrite of an existing dashboard). Credential references are environment variables only. Monaco platform token permissions differ from the ingestion token: use existing secure storage for an authorized configuration identity; do not repurpose or expose the Firebase ingest credential.

1. Check the connected tenant and download any existing configuration before updates. Review ownership/IDs to avoid duplicates or replacing manual changes.
2. Set `DT_ENV_URL` and `DT_PLATFORM_TOKEN` through the existing secure workflow, then run `monaco deploy --dry-run observability/manifest.yaml`. Validate against the actual tenant Settings schema. Dry-run is not installation.
3. After deployment authorization, apply the reviewed config with Monaco and import the reviewed dashboard. This repository does not run these writes from PR CI.
4. Verify source version/revision and the new metric identities in the tenant, then verify alert evaluation and recovery with approved fixtures. Review the automation execution identity and notification routing before enabling alerts. Do not create test failures in learner records.

The scheduler samples outbox aggregates every five minutes. `learningTelemetryHealth/backlog` stores only bounded `{at,pending}` history, never event bodies or learner identifiers. The growth gauge becomes 1 only after a strictly increasing sequence spanning at least fifteen minutes, with no observation gap over seven minutes. Duplicate invocations cannot manufacture evidence; a flat/decreasing count or gap breaks the sequence. Alerts evaluate one-minute buckets; missing samples are unknown. The 15-minute condition is computed from durable observations rather than filling missing samples with fabricated zeroes. Allow an additional query offset of three minutes for ingestion.

The oldest pending age is emitted only when the bounded 501-document sample proves completeness (at most 500 pending). Counts use aggregation; age null/missing is not zero. Inspect the admin UI for that limitation. Health reads are separate observations, not a transactionally consistent financial snapshot.
